# Монітор доступності API (`api_monitor.py`)

Скрипт перевіряє доступність списку HTTP/HTTPS цілей, класифікує типи збоїв на різних етапах мережевої взаємодії та надсилає сповіщення у месенджер при виявленні проблем.

## Запуск

1. Встановіть залежності:
   ```bash
   pip install requests
   ```
### Чим «з'єднання відхилено» відрізняється від «тайм-аут» і чому в реальному інциденті ці два випадки ведуть до різних дій.

«З'єднання відхилено» означає, що мережевий шлях і сам хост працюють, але операційна система сервера відразу повертає відмову, бо на потрібному порту жодна програма не слухає сокет.

«Тайм-аут» означає, що за відведений час відповіді немає взагалі — пакети мовчки відкидаються, мережевий маршрут обірвано або хост повністю знеструмлений/недоступний.

При Connection Refused копають всередині сервера: Оскільки хост відповідає, проблема локальна. Інженер перевіряє статус додатка (systemctl status, docker ps), логи падіння (чи не впав процес через OOM/Crash) та конфігурацію портів.

При Timeout копають мережу й інфраструктуру: Відповіді немає, тому шукають перешкоду на шляху до сервера. Інженер перевіряє правила мережевих файрволів (AWS Security Groups, cloud firewalls), таблиці маршрутизації, VPN-шлюзи або чи живий сам хост (ping, traceroute).

# Git-хуки

У папці `hooks/` знаходяться локальні скрипти автоматичної перевірки:
* `pre-commit` — перевіряє лінтером лише ті `.sh` та `.py` файли, які додано в staged.
* `pre-push` — запускає автоматичні тести перед відправкою коду у віддалений репозиторій.

---

## Інструкція зі встановлення хуків

Оскільки папка `.git/hooks/` не версіонується Git і не передається між розробниками, скористайтеся одним із методів встановлення:

### Спосіб 1. Через налаштування `core.hooksPath`
Вказує Git використовувати вашу папку `hooks/` замість `.git/hooks/`:

```bash
git config core.hooksPath hooks
```

### Спосіб 2. Через символічні посилання (Symlinks)

```bash
ln -s ../../hooks/pre-commit .git/hooks/pre-commit
ln -s ../../hooks/pre-push .git/hooks/pre-push
```

### Спосіб 3. Звичайним копіюванням

```bash
cp hooks/pre-commit .git/hooks/pre-commit
cp hooks/pre-push .git/hooks/pre-push
chmod +x .git/hooks/pre-*
```

---

## Чому Git-хуки не є засобом контролю якості

1. **Локальне виконання та простий обхід**:
   Git-хуки виконуються виключно на робочій машині розробника. Будь-хто може легко обійти перевірку хука, додавши прапорець `--no-verify`:
   ```bash
   git commit -m "fix" --no-verify
   git push --no-verify
   ```
   Також розробник може банально видалити хук зі своєї папки `.git/hooks/` або вимкнути виконання скриптів.

2. **Відсутність централізованої гарантії**:
   Адміністратор репозиторію не має технічної змоги примусово змусити клієнтський Git виконати локальний хук.

---

## Що роблять обов'язкові перевірки в конвеєрі (CI/CD Pipeline), чого не можуть хуки

* **Гарантований централізований контроль (Central Enforcement)**:
  CI-конвеєр (наприклад, GitHub Actions чи GitLab CI) виконується на ізольованому віддаленому сервері, який контролюється організацією, а не розробником.

* **Правила захисту гілок (Branch Protection Rules)**:
  Усі Pull/Merge Request блокуються для злиття в захищені гілки (`main`, `release`), якщо статус перевірок CI не дорівнює `Success`. Обхід прапорцем `--no-verify` на рівні CI неможливий.

* **Відтворюване середовище (Reproducible Environment)**:
  CI запускає перевірки та тести в чистому контейнері з чітко зафіксованими версіями залежностей. Це повністю виключає проблему «на моєму комп'ютері все працювало».

* **Прозорість та аудійованість**:
  Результати та детальні логи виконання CI збережені централізовано й доступні усій команді для аналізу та рев'ю.
