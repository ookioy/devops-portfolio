Чому значення core.autocrlf різне для Windows і Unix і що станеться в команді зі змішаними системами, якщо його не задати?
- У Windows при переході на новий рядок пишеться невидимий символ CRLF, що означає перейти на новий рядок і змістити курсор, тому вмикається (true) core.autocrlf, для того щоб автоматично після завантаження в репозиторій CRLF помінялось на стандартизований LF.
- Для Unix систем використовується значення input (рекомендовано) або false оскільки тут за замовчуванням пишеться LF замість CRLF.
- Якщо ж у команді будуть використовуватись різні значення, тоді можуть виникнути конфлікти при merge.

Чим історія з pull.rebase=true відрізняється від типової?
- В типовому pull після виконання - вилка комітів буде розгалужена; а при pull.rebase=true - вилка комітів буде чергуватись.

Навіщо менеджер версій, коли проєктів більше одного?
- Припустимо що розробник повинен працювати з декільками проектами. В одному проекті використовується остання версія python, а в іншому передостання. Якщо б не було менеджера версій, то прийшлось би кожного разу для роботи з конкретним проектом перевстановлювати python до потрібної версії. Завдяки менеджеру версій можна міняти версії однією командою.

- sudo docker --version Docker version 29.8.0, build 88096ef

Чому приватний ключ ніколи не потрапляє в репозиторій і що робити, якщо він усе ж туди потрапив?
- Ключ може потрапити у репозиторій лише у разі якщо сам користувач додасть його до репозиторію.
- При потраплянні приватного ssh ключа в репозиторій, існує загроза несанкціонованого входу від імені користувача ключ якого потрапив в публічний репозиторій.
- Якщо ж він усе таки потрапив потрібно:
1) згенерувати новий ssh ключ
2) видалити старий ключ
3) перевірити історію логів після пушу ключа
4) видалити файл ключа з історії репозиторію
5) заблокувати ssh-ключі у .gitignore та локальній конфігуряції, щоб не повторювати помилку

Що саме зміниться в налаштуваннях, коли робота стане командною?
- створиться bypass list, а також треба буде додати рецензію коду. Тобто схвалення коду іншим розробником перед заливом.

Чому «заборона обходу правил адміністратором» безпечна в команді й шкідлива соло?
- Це може критичною помилкою для соло, оскільки "заборона обходу правил адміністратором" вимагає схвалення коду від іншого розробника, і тоді система не дозволить залити код адміністратору і може зламатися репозиторій. Для команди це саме те, оскільки допоможе виключити людский фактор з проекту (хоча б частково).
